# 岐黃尋・系統優化規劃

> 核心參考規則（來自笈成檢閱系統 v1.4.8 `objects.js`）：
> `queryMax: 20` — 搜尋範圍超過上限時，**明確告知使用者**「您選了 X 本書，但系統限制每次最多處理 20 本，已自動取消選取多餘項目」，而不是悄悄過濾。
>
> 這條規則背後的設計哲學是本次優化的地基：**寧可誠實地縮小範圍，也不要在使用者不知情的狀況下犧牲資料完整性。** 岐黃尋目前的 `MAX_CANDIDATE_BOOKS = 60`（依字數由小到大截斷、無提示）正好違反了這條規則，這也是目前「問題那麼多」的根源。以下規劃分四層，把這條規則落實到岐黃尋的每一層架構。

---

## 一、問題盤點（現況）

| 層級 | 現況問題 |
|---|---|
| 候選排序 | `sort by charCount asc` + `slice(0, 60)`，字數大的典籍（本草綱目 187萬字、普濟方 538萬字）系統性被排除，且無任何提示 |
| 網路請求 | 多字查詢的 bigram 分片是 `for` 迴圈內 `await`，序列請求，未平行化 |
| 資料粒度 | 每本典籍是單一 JSON 檔，大書（普濟方 5.38M 字）驗證時要整包下載 |
| 使用者感知 | 沒有任何「範圍受限」「還有 N 部未檢查」的訊息，使用者誤以為是完整全文檢索 |
| 主執行緒 | 候選驗證、字串比對都在 main thread 執行，資料一多會卡 UI |
| 文件一致性 | README 寫 80，程式碼是 60 |

---

## 二、設計原則（把 jicheng 的規則抽象化）

1. **範圍限制永遠要「講出來」**：任何截斷、跳過、簡化都要在 UI 上明示，並提供使用者可控的「繼續 / 縮小範圍」選項。
2. **截斷順序要跟「相關性」掛鉤，不能跟「書的大小」掛鉤**：目前用 charCount 排序是誤把「資料成本」當「相關性代理指標」，必須換成真正的相關性分數。
3. **大書的問題該用「拆分」解決，不是用「排除」解決**：本草綱目大，不代表要被丟掉，而是它的「取用單位」應該變小（按卷/章拆分），這樣既降低單次下載成本，又不犧牲完整性。
4. **搜尋應該是漸進式、可中斷、可恢復的**（像 jicheng 的可暫停佇列），而不是一次性阻塞到底。

---

## 三、系統重構規劃

### 3.1 資料層：把「大書」拆成「小單位」＋ manifest 指標檔

- 建置索引時，依現有的 `chapterTitles` 章節結構，把每本典籍的內容拆成**章節級 JSON 分塊**（每塊建議控制在 50–150KB），取代現在「整本書一個 JSON」的做法。
- 不要讓前端直接猜分塊路徑，改成**一個極小的 manifest 指標檔**指向實際分塊位置，例如：
  ```json
  // data/books-manifest.json（整份可能只有幾十~幾百 KB）
  { "普濟方": [{"chunkId":"pjf_001","chapterTitle":"卷一","file":"books/普濟方/001.json"}, ...] }
  ```
  這個模式不是憑空設計，是已經有人在同類場景（靜態站中文全文檢索）實測驗證過的做法：有開發者原本把索引塞成單一大 JSON，檔案一到 9.7MB 首屏解析就直接卡死主執行緒，後來改成「manifest 指標檔（幾十 bytes）+ 依內容分片」才解決，這跟岐黃尋「普濟方整包 5MB+ 下載」是同一類已知陷阱。manifest 模式比直接拆檔案更有彈性：之後要調整分塊粒度（例如發現某些章節還是太大要再切），只要重建 manifest，前端邏輯完全不用改。
- 效果：驗證候選典籍時，只需下載「含有該關鍵字所在章節」的那幾個分塊，普濟方 538 萬字的書，實際下載可能只需其中幾十 KB，而不是整包 5MB+。這是解決「大書拖慢速度」的根本方法，比排除大書更好。

### 3.2 索引層：從「是否命中」升級成「命中強度」

- 目前 bigram 分片只記錄「這個 bigram 出現在哪些書」（布林命中）。建議在建置索引時，額外記錄**詞頻（每本書每個 bigram 出現次數）**，例如：
  ```json
  { "75db": { "4e2d": [[12, 3], [45, 1], [201, 27]] } }
  // 格式: bigram -> { 下一字bigram: [[bookIndex, hitCount], ...] }
  ```
- 查詢時，把命中的所有 bigram 的 `hitCount` 加總，作為該書的**相關性分數（近似 TF）**，取代現在單純「存在/不存在」的二元判斷。
- 候選排序改為**依相關性分數由高到低**，而不是依字數由小到大。這樣本草綱目如果真的高度相關（命中次數多），會自然排到前面；如果只是偶然出現一次，本來就該排到後面——這才是「截斷」該有的邏輯。

### 3.3 查詢層：平行化 + 分批漸進式輸出

- 修正 bigram 分片抓取：
  ```js
  // 現況：序列 await，一個一個等
  for (let i = 0; i < q.length - 1; i++) {
    const shard = await getShard(bigram[i][0]);
  }
  // 改為：平行抓取
  const shards = await Promise.all(
    bigrams.map(bg => getShard(bg[0]))
  );
  ```
- 拿掉硬性 `slice(0, 60)` 的靜默截斷，改為：
  1. 一次算出全部候選並依相關性排序。
  2. **先驗證＋顯示相關性最高的一批（例如 30 部）**，結果即時渲染，不等全部跑完。
  3. UI 顯示「符合條件的典籍共 N 部，已為您顯示相關度最高的 30 部」+「繼續載入下 30 部」按鈕，讓使用者自己決定要不要往下挖——這正是 jicheng `queryMax` 那個 alert 的精神，只是做得更友善（用可繼續載入，取代單純警告）。
  4. 全部驗證/渲染流程比照 jicheng 的「可暫停 queue」設計，讓使用者能隨時停止長查詢。

### 3.4 效能層：搬出主執行緒

- 把 bigram 交集運算、章節文字比對搬進 **Web Worker**，避免大量候選驗證時卡住輸入框和捲動。同類場景已有實測案例：把子串檢索搬進背景 Worker 執行、拉分片與比對都不佔用主執行緒，UI 全程不卡頓——是可以直接照搬的作法，不是理論上的優化。
- 輸入框加 **debounce（約 200–300ms）**，並在使用者繼續輸入時，主動 `abort` 前一次尚未完成的 fetch，避免舊查詢結果覆蓋新查詢畫面。

### 3.5 UX 層：向 jicheng 借的「範圍先行」概念（可選，加分項）

- 可加入「分類 / 朝代」篩選（複選），讓進階使用者能像 jicheng 一樣先縮小範圍再搜，滿足「想要更快、更精準」的重度使用者；一般使用者仍可直接全庫搜尋，只是會看到分批結果。這不是憑空建議：同量級的大型古籍全文檢索系統（例如佛教藏經 CBETA 的第三方閱讀器）也是這樣設計——使用者不需要記得精確原文就能搜到結果，並且提供依典籍類目、作譯者年代等條件過濾搜尋結果，屬於這個規模的古籍檢索系統的標準配置，不是加分項而已。

### 3.6 架構層：現有「bigram 子串比對」選型是對的，不用改成分詞

- 額外確認一件事：岐黃尋現在的作法是「拆連續雙字元、逐字比對」，**不做中文分詞（斷詞）**。這個選型是對的，不需要為了「更聰明」而改成 jieba 之類的分詞方案。已有同類場景的實測對比：中文查詢一旦先分詞再比對，容易把「限寬墩」這種固定詞組拆散、反而搜不到本來該命中的內容；改回連續子串比對後才真正抓得到。病名、藥名、方劑名這種必須完整命中的固定詞組，子串比對本來就比分詞更準——這條不用動，維持現狀即可。

### 3.7 維運層：小修正

- `MAX_CANDIDATE_BOOKS`／README 數字對齊，並把這類常數集中定義成單一 config 檔，避免文件與程式碼再次脫鉤。
- 移除或搬移 `diagnostic.html`、`diagnostic2.html`、`test_fetch.html` 等除錯用頁面到獨立的 `/dev` 目錄或直接移出正式部署範圍，避免使用者誤入。

## 五、外部參考案例

盤點 GitHub 與相關技術社群後，沒有找到可以整包套用的「現成中醫古籍前端全文檢索引擎」——多數中醫典籍相關 repo（如 daizhige、TCM-Ancient-Books）只是純文本資料集合，不含檢索系統本身。但兩個相鄰場景的實戰經驗值得參考：

- **同為「純靜態網站 + 瀏覽器端中文全文檢索」的個人專案**：踩過「單一大 JSON 拖垮首屏」的坑，最終解法是 manifest 指標檔＋內容分片＋Web Worker 執行檢索，並驗證了連續子串比對比分詞更適合處理固定詞組——這些結論已經整合進第 3.1、3.4、3.6 節。
- **CBETA（佛教大藏經）第三方閱讀器**：量級與岐黃尋相近（上萬部經、上億字），標準配置包含模糊檢索與依類目/年代篩選結果，印證第 3.5 節的分類篩選建議並非錦上添花。

## 六、一句話總結

jicheng.tw 的「快」不是資料量小，而是它**誠實地把範圍限制講清楚**；岐黃尋要做到「又快又完整」，關鍵不是模仿它的範圍限制數字，而是把「限制」從**依大小的靜默犧牲**，換成**依相關性的透明分批**（已上線），並用**拆章節分塊＋manifest＋Web Worker**（同類場景已驗證有效的做法）從根本降低大書的存取成本與主執行緒負擔。
